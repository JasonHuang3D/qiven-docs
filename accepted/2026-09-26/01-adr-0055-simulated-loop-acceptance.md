# ADR-0055 (draft): Simulated ZCode Hook Lifecycle as the Interim MVP-4 Gate

> Status: PROPOSED in qiven-docs PR #4. This document changes no current Runtime or Context gate until the owner accepts a specific canonical amendment. Related: [four-trial evidence audit](02-h1-trial-history-and-defect-evidence.md), [compaction and continuity proposal](../2026-09-26/00-compaction-continuity-and-h1-simulation.md), [custom-subagent qualification](../2026-09-26/01-custom-zcode-subagent-qualification.md), [Devkit gate audit](04-devkit-standards-and-precedent-gate.md).

## 1. What this proposal changes

The owner now directs MVP-4 H1 toward **tests that simulate the real ZCode invocation sequence** while Runtime and a separately controlled context mechanism are unfinished. The current [ADR-0050 decision 8](https://github.com/JasonHuang3D/qiven-context/blob/main/decisions/ADR-0050.md) still says to rerun a **real H1**; [ADR-0047 decision 6](https://github.com/JasonHuang3D/qiven-context/blob/main/decisions/ADR-0047.md) also describes real tool-entry proof. This PR proposes a *narrow replacement for the interim MVP-4 development gate*: execute the actual Qiven hook and RuntimeHost with a simulated ZCode caller and exact, independently sourced event shapes. Accepting this proposal requires an owner-approved amendment to both decisions, the Runtime exit matrix, active obligation and current state. Before that transaction the real-H1 exit is still OPEN. After it, a passing result may be reported as `MVP4_SIMULATION_ACCEPTED`, never as execution proof of the installed Windows Desktop carrier.

The 2026-09-25 PoC affected the owner's official installation and browser. The interim rig does not build, launch, redirect or mutate any real ZCode Desktop or CLI harness component on the owner's machine. It reads pinned source and recorded payloads; it runs only Qiven's hook/host binaries in an isolated temporary root with a local scripted counterpart where required. A later real-carrier trial needs separate authority and a genuinely disposable environment. This proposal creates no requirement to transplant the ZCode CLI or to complete a Foundation refactor before building the test.

## 2. Independent caller contract

The test driver must model the actual hook lifecycle, **not call a host handler directly and label it ZCode integration**. Derive fixtures from a pinned [official ZCode hooks implementation](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/apps/zcode-cli/packages/core/src/runtime/methods/hooks.ts), published hook payload contracts, and the historical H1 captures, with each fixture's revision and provenance recorded. Historical captured behavior and source analysis answer different questions; if the installed Desktop identity/configuration does not map to the pinned source, label the discrepancy. Do not assume the source tree is the packaged carrier.

The Windows driver launches the **candidate production hook executable** as an external process with the exact stdin JSON and environment form it is supposed to receive, and runs the **candidate RuntimeHost** behind the actual named pipe and packaged profile/configuration. The simulator replaces only the caller and external inputs. It must assert emitted replies, stable session identity, journal events, absence of unintended effects, process exit and bounded time, not merely that two processes exchanged bytes. An independently specified expected verdict (accepted contract or recorded incident), never the current implementation's output copied into the fixture, is the oracle.

| Lifecycle case | Required observation | Discriminating negative |
| --- | --- | --- |
| SessionStart with source `startup`, session handle, CWD and declared mediated tool inventory | Hook sends hello **and** `session_start` event on the real connection; host registers one session, journals it and returns a correlated identity and typed verdict. A repeat start is idempotent. | The old one-frame host or hello/event deadline split cannot satisfy registration under the same request budget. A pipe echo without a journal row fails. |
| PreToolUse in the registered, healthy session | A governed Write/Edit/Bash mutation denies in the specified class without executing an effect; an outside-scope case is `not_governed` only under its real preconditions. | Without SessionStart, with unknown tool, missing admission/configuration, expired cognition or mismatched manifest, the affected action fails in its specified class; “any verdict” is not a pass. |
| PostToolUse and lifecycle closure | Correlation refers to the correct earlier call/session; shutdown, restart, duplicate IDs and a new session preserve the intended journal and isolation contract. | A PostToolUse from an unregistered or mismatched session cannot be silently accepted as success. |
| Packaging and path forms | The shipped kit resolves its profile from its own root; selected Windows alias/reparse/relative/Unicode fixtures give their expected conservative result. | A CWD profile that happens to exist cannot substitute for a missing kit profile; lexical prefix alone cannot claim filesystem authorization. |

Include the observed trial-1 absent field, trial-2 borrowed-payload lifetime, trial-3 hello/event and admission mismatch, trial-4 total deadline, and the separate kit-preflight incident as **distinct** cases. Exercise a full hello/event transaction within one monotonic hook timeout; a one-frame or per-frame-only timer cannot close trial 4. Make each case fail on the historical defective revision or on an explicit fault injection for the same reason, pass on the candidate, and include a plausible wrong fix that the test rejects. The owner's previously requested 100 named deterministic experiments remain a breadth target; coverage of invariants and discriminating cases decides whether they are meaningful. The owner can amend the numeric floor explicitly during acceptance; a count alone is never a verdict.

The existing [`h1_kit_test.py`](https://github.com/JasonHuang3D/qiven-runtime/blob/7b3ce515774de8f146aefc066ffbf0e69e2e33a4/tools/h1_kit_test.py) tests packaging but reports a successful return when the host executable is absent and its process case prints `[SKIP]`. A required H1 simulation gate must turn a skipped host/hook/scenario into **NOT_RUN / failure for acceptance**, never a green receipt. Keep the useful packaging checks, then add the lifecycle rig rather than counting the existing script as H1 proof.

## 3. Source and carrier boundaries

Read-only analysis of the pinned ZCode source checks event dispatch, tool inventory, denial application and any unmediated child/subagent tool path. A simulator cannot demonstrate that the installed Desktop fires hooks under every configuration or that a provider obeys them. Source parity is a documented assumption, not a test oracle; a different build or runtime configuration invalidates the relevant claim. The [pinned child construction](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/apps/zcode-cli/packages/core/src/runtime/methods/subagent.ts) does not wire hooks into subagent tool calls. Built-in general-purpose retains write/command tools; a separately configured read-only reviewer does not remove that path. If an uncovered delegation/tool path can write inside the governed root, the complete-mediation claim is blocked even when the simulated main session passes. Include the writable-child bypass as a negative coverage case; do not count a read-only child as proof of mediation.

Report separate states for `SIMULATED_HOOK_HOST_PASS`, `PINNED_SOURCE_CONTRACT_REVIEWED`, and `INSTALLED_DESKTOP_EXECUTION_UNVERIFIED`. An absent required fixture, skipped platform leg, changed source/profile digest or missing registered-session negative control makes the simulation state NOT_VALIDATED. This distinction is part of the proposed replacement for real H1, not a claim that a simulator reproduces all Desktop behavior.

## 4. Gate trigger and compaction limit

Bind the fixture catalogue, expected outcomes, candidate Runtime/Hook/Foundation/Devkit source graph, profile digest, platform/toolchain and actual test command to a receipt. Run the relevant suite on the **same candidate** before publishing an MVP-4 acceptance claim and again whenever the relevant hook/IPC/profile inputs change. A gate that merely exists in the repository, or runs on an older locked graph, is not proof. The Devkit/Context activation path must make the test obligation visible at the task boundary, and the build/PR publication gate must reject absent, skipped, stale or failed receipts.

Neither the test corpus nor a SessionStart hook makes the work model remember its purpose after a later context compact. [The ZCode source](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/apps/zcode-cli/packages/core/src/runtime/methods/turn-loop.ts) checks compaction before individual model steps, while SessionStart is a session lifecycle event. The proposed continuity control must re-select active obligations for the relevant task at subsequent boundaries and, ultimately, at each normal model request in a controlled harness. Until that request-boundary path exists and is tested, the interim gate can block *publication of an unproven candidate* but cannot promise that every intermediate model decision used all intended context. See the [continuity proposal](../2026-09-26/00-compaction-continuity-and-h1-simulation.md).

## 5. Acceptance transaction and limits

Owner acceptance of this revised MVP-4 standard must state in one canonical transaction: the replaced clauses of ADR-0047/0050, the simulated gate command and platform, required cases, coverage and skip policy, receipt identity, the precise label `MVP4_SIMULATION_ACCEPTED`, and the surviving unverified Desktop scope. Keep later MVP/CA dependency transitions aligned with that newly agreed label; no document-only proposal changes current sequencing. No owner-machine real-harness run, ported CLI, wholesale Foundation program or claimed Desktop equivalence is a prerequisite for the *simulation* gate. Before PR4 document acceptance, independently qualify the proposed [custom read-only reviewer](../2026-09-26/01-custom-zcode-subagent-qualification.md) on the intended ZCode installation; that qualification is a deliberation safeguard, not the H1 simulation result and not proof of child-hook coverage. Separate lower-level code defects identified by the tests still need correct fixes at their semantic owners, with the same old-fail/new-pass evidence.
