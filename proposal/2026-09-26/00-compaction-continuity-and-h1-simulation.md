## 1. Owner reflection and evidence classes

The owner observed that earlier Qiven work repeatedly reuses an old implementation or design despite documented corrections. Their present hypothesis is that **context compaction and loss of task-relevant intent across model requests are a major recurrence mechanism**. Real lower-level infrastructure gaps and the four H1 defects also exist; the compaction hypothesis does not erase them. Nor do those incidents alone prove how much of each failure came from compaction rather than retrieval, stale entry points, missing tests, weak review or a genuine software contract error. Measure the mechanism before presenting it as the sole historical cause.

In the owner's conceptual model, Tier 0 is the harness/prefix constraint surface, Tier 1 the recent working set, Tier 2 semantically summarized decisions and intent, and Tier 3 old logs and tool outputs. This is a **risk taxonomy**, not a four-tier ZCode API or an assurance that the first two tiers are always reliable. In pinned [ZCode `turn-loop.ts`](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/apps/zcode-cli/packages/core/src/runtime/methods/turn-loop.ts), the runtime checks microcompact and auto compact before each normal model step, including steps within one user turn. [Microcompact implementation](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/apps/zcode-cli/packages/core/src/runtime/methods/microcompact.ts) is a **local tool-result rewrite when enabled and triggered**, not an LLM call on every step. [Full compact](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/apps/zcode-cli/packages/core/src/runtime/methods/compact-active.ts) makes a separate model-backed summary request, then replaces history with the summary and selected retained entries. The [selection code](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/apps/zcode-cli/packages/core/src/runtime/helpers/compact-selection.ts) retains a recent round only under particular triggers and available groups. The prefix is handled structurally; the model can still misuse it, and dynamically loaded skills/older file reads are not automatically protected because someone considers them important. These facts concern the pinned CLI source; installed Desktop build/configuration equivalence has not been established.

A summary may preserve a decision's words while dropping its provenance, conditions or counterexample. It may also turn a tentative owner's thought into an accepted sounding mandate. A model can request a file again; no normal task request automatically knows what vanished. The earlier PR4 additions that elevated a brainstorming direction into wholesale Foundation and ZCode-transplant requirements are a **candidate example of intent/status drift**, not forensic proof that a particular compact event caused that revision. Record the prior wording and this owner correction as evidence with distinct status.

## 2. What a test gate can and cannot do

An invariant can survive model forgetting when an **external executor actually runs a test and blocks publication on failure**. For MVP-4, a simulated real hook invocation with independent payload fixtures can expose absent SessionStart, a one-frame host, a wrong deadline or a skipped binary, even if the author has lost the relevant discussion. Such a test does not reinsert the owner's original intent into the model. To give the work model the reason and source, a trusted boundary must also deliver a concise, current activation receipt **before the relevant model decision**, and return the test result with a link to its authoritative contract.

A text instruction saying “remember to run the test” has no such guarantee. A CI test with no enforced task/PR trigger, an old receipt, or a `[SKIP]` counted as PASS also provides no gate. SessionStart hook injection occurs at session start, not before every model request. PreToolUse can block a covered main-session tool action, but cannot prove arbitrary model design reasoning and misses current ZCode child tool calls. Until an owned request-boundary adapter exists, interim controls are **partial**: they can protect named code publication/acceptance boundaries; they cannot claim compaction has been solved for all reasoning. A newly spawned reviewer has separate context and can challenge the work model's assumptions when given a clean, exact-source brief. [Qualification before PR4 acceptance](01-custom-zcode-subagent-qualification.md) narrows its tools and verifies the transcript; its output remains candidate evidence, never recovered or intrinsic authority.

## 3. Interim contract while the harness is unfinished

1. **Select from sources, not from remembered prose.** At each task admission and materially changed scope, resolve the current owner-accepted constraints, live document status and known scars from exact Git-backed revisions. Keep proposal/accepted/historical status typed; a PR4 draft cannot become canonical because a compact summary repeats it. Reuse ADR-0050's task-time activation path and the Devkit entry-point repair; do not revive the sealed write-coupled Python ContextKernel or create a competing retriever.
2. **Bind an obligation to a detector.** For MVP-4 use an invariant-to-test map: `SessionStart registration -> lifecycle fixture/journal oracle`, `hello + event deadline -> complete real-pipe exchange`, `payload lifetime -> historical negative`, `kit profile -> CWD-independent launch`, and `unmediated tool path -> explicit residual/no complete-mediation claim`. Each row cites an accepted contract or evidence source, required test IDs, tested graph/platform and freshness rule. An unresolved placement question (`qiven::fs`, vendor, repository boundaries) is recorded as a decision to review, not made a hidden prerequisite of H1.
3. **Run and return results at an enforced boundary.** The operator/CI publication step must launch the named tests for the exact candidate, treat absent/skipped/stale results as NOT_VALIDATED, and return a short result to the work model identifying failed invariant, test, source and next action. Mark interim manual portions honestly; a passive Markdown checklist is not a hard control. If the model can publish around this operator, record that bypass and restrict the claim accordingly.
4. **Observe actual coverage.** Record whether a task hit the selector, whether the model received the source-bound activation receipt before design, whether a compact boundary intervened, whether a qualified fresh reviewer received an artifact-only brief, whether tests ran before publication and whether a different decision was made after the result. Exercise a replay with a deliberately lossy summary and a seeded previous-code error; failure to activate, detect the defect, or block the bad candidate is a counterexample. These experiments assess the control, not an unobservable guarantee that the model “remembered.”

The PR4 document museum, Devkit admission fixes and Context status repair reduce stale boot-time inputs. The simulated H1 gate gives a separate machine-checkable signal for one real boundary. Both may be useful; neither substitutes for an enforced request-time activation mechanism.

## 4. Later harness integration, with a measured handover

A future Qiven-controlled harness adapter can inspect **every normal model-request boundary**, including those after microcompact and full compact, select the task-relevant source closure and inject the minimum source-identified, current obligations before the model acts. Keep mandatory policy outside the summarizing model; preserve request receipts and demonstrate missing/stale/withheld/late activation failures. Treat compaction itself as a separate request whose summary is data, never an authority promotion. Check long turns with multiple tool calls, resume, source change, prompt overflow and delegated tool paths. If the integration cannot observe a boundary, it must report a coverage gap rather than infer success from a green unrelated test.

Do not disable ZCode's full compact solely because a local roughly 8B model can write a summary: context budgeting, fidelity, source activation and overflow recovery need a tested replacement. The same work model may still lose information even after switching summarizers. A controlled handover requires bounded prompt/request tests, a current authority reconstruction independent of summary text, a rollback, and evidence on the actual intended Desktop carrier in a safe environment. This is future design work; the present PR modifies only qiven-docs.
