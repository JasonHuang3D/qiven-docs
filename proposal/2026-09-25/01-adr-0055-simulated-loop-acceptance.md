# ADR-0055 (draft): Deterministic Mediation Verification with an Explicit Desktop Claim Boundary

> Status: PROPOSED for owner adjudication and canonical landing in `qiven-context`. Companion: [ADR-0054](00-adr-0054-typed-identity-law.md), [evidence audit](02-h1-trial-history-and-defect-evidence.md), [Foundation architecture/museum audit](03-foundation-architecture-and-museum-transition.md), [Devkit standards/precedent audit](04-devkit-standards-and-precedent-gate.md), [Host/DCR retirement audit](05-retire-host-dcr-and-native-doc-authority.md), [Foundation infrastructure study (exploratory)](../2026-09-26/00-foundation-infrastructure-study.md), and [ZCode harness vehicle study (exploratory)](../2026-09-26/01-zcode-harness-vehicle-study.md).

## 1. Decision and exact supersession

Replace the **four-failure owner-operated GUI probe sequence** as the routine *mechanical mediation verification* method with a scripted, reproducible rig over the real hook, the real host, captured real harness payloads, and pinned harness source — **without executing any real harness on the owner machine**. Whether this evidence can replace any portion of the **real H1 exit** requires explicit owner adjudication and canonical amendment of [ADR-0050 decision 8](https://github.com/JasonHuang3D/qiven-context/blob/main/decisions/ADR-0050.md), its active obligation/roadmap, and the **real H1 tool-entry proof** in [ADR-0047 decision 6](https://github.com/JasonHuang3D/qiven-context/blob/main/decisions/ADR-0047.md). These older clauses remain authoritative until the owner accepts and the canonical contracts/state are amended; the PR itself changes no gate. [ADR-0036's handoff boundary](https://github.com/JasonHuang3D/qiven-context/blob/main/collaboration/human-handoff-boundary.md) remains applicable to owner-only credentials, external isolation, owner-named trust anchors and adjudication; this proposal does not waive those classes. [ADR-0049's H1 kit standard](https://github.com/JasonHuang3D/qiven-context/blob/main/decisions/ADR-0049.md) remains in force for future actual H1 packages.

The user-facing target is a **Windows ZCode Desktop session** under `zcode-jason-context-record-mvp`. The rig tests the mediation contract at the real hook/host boundary and investigates the pinned harness contract using source analysis and captured real payloads; it never builds, executes, or mutates any real ZCode component on the owner machine (Layer 2, §2). Executed live-carrier proof — running the installed Desktop application or any source/dev-mode build of the harness on this machine — is outside the rig's scope: the 2026-09-25 harness PoC demonstrated that such execution is an unfalsifiable isolation claim on this machine (source/dev-mode execution contaminated the running official installation's state, still visible in the production UI, and forced a browser reinstall; qiven-context memory `MEM-20260925T190500Z-C0A1B2`, with the owner confirming the damage was worse than first recorded, 2026-09-26). Any future live-carrier exercise requires a genuinely disposable environment (for example a VM) and an explicit owner decision; it is never a default acceptance step. The acceptance report must label the precise carrier and the precise class of evidence it proves.

## 2. Two verification layers

**Layer 1 — real hook/host, scripted payloads.** On Windows, invoke the production hook executable and production RuntimeHost through the real pipe, with a fresh isolated installation and captured/pinned harness payload schemas. Exercise the *entire session lifecycle*: boot, SessionStart registration, capability check, PreToolUse for Bash/Write/Edit, PostToolUse correlation, shutdown, and new-session/restart cases. Run both positive and negative controls. Assert response **class** and journal state, not merely that a pipe round trip returned something: SessionStart must create exactly the expected session; a governed mutation must deny without a transaction that executes an effect; an outside-scope action in a *registered, healthy* session must be `not_governed`; missing host/admission/replay/version/secret skew must fail in their specified classes. Include the trial-4 hello/event deadline regression, trial-3 multi-frame and admission regressions, trial-2 payload-lifetime regression, trial-1 absent-payload-field regression, and the separate kit-entrypoint failure. Use real filesystem fixtures for aliases, relative bases, Unicode and reparse/ambiguous cases where the declared scope requires them.

The scenario catalogue is a versioned matrix keyed by **boundary and invariant**, with an explicit coverage map and a failing historical implementation/negative control per incident. Run at least 100 named deterministic experiments as the owner's mandatory breadth floor, and require the boundary/invariant coverage map to pass; the number alone is not sufficient and a Cartesian product of impossible states has no value. Preserve the owner's six original probes as a named subset, but do not treat six probes as the complete matrix. Layer 1 is a Windows gate task; the accepting candidate must have a successful run at its exact head.

**Layer 2 — harness contract evidence without harness execution.** Three legs support bounded claims about the pinned harness revision; none builds or executes a real harness on the owner machine, and together they do not constitute executed Desktop proof:

1. **Pinned-source contract analysis.** The harness revision's relevant code paths — tool-call parsing, hook invocation and payload construction, decision application (including `updatedInput`), deny/exit-code enforcement on the tool executor, provider transport, and the delegation (subagent) boundary — are analyzed from source at a pinned revision, and the asserted contract is recorded as named source facts (file and symbol level, as the v30 source review already demonstrated). A harness revision change re-runs the analysis; mechanically checkable assertions (symbol and structure presence) may be scripted against the source tree statically.
2. **Captured-payload replay.** The real harness payload streams captured in the four owner-live trials and the kit-preflight incident form the replay corpus; Layer 1's driver replays them against the real hook and real host to prove the mediation contract under the real harness's input shapes, including the multi-frame and deadline behaviors that actually failed.
3. **Historical behavioral evidence.** The trials record behavior of the particular installed carrier/configuration and tested tool entries at their historical time. The deny-118 incident supplies repeated evidence of hook denial on those entries; it does not prove every present or delegated tool path, a later installed build, or equivalence to the pinned CLI source.

The delegation boundary remains part of the pinned contract: at the recorded harness revision, subagent child runtimes are constructed without a hook runner, so no PreToolUse hook fires inside subagent tool calls (`MEM-20260926T195500Z-F1E2D3`, verified against the pinned source and corroborated live). The profile must be proven — at the host/policy level and in the source analysis — to deny or not admit the delegation tool entry in a governed main session, or the unmediated subagent path is recorded as a labeled residual; a green main-session scenario set does not cover it.

Layer 2 is a reproducible evidence artifact bound to the **exact Runtime candidate plus the analyzed harness revision**, and is redone when relevant harness source or configuration changes. The [vehicle study](../2026-09-26/01-zcode-harness-vehicle-study.md) may assess an executable derivative or a smaller driver. If one is later built, its run is labeled as evidence of **that vehicle at its exact revision**, with a separate fidelity assessment; it never automatically becomes proof for the installed Desktop or a mandatory MVP-4 exit condition.

Static analysis, replay and historical behavior support only their stated source/configuration, input and temporal bounds. They do not prove real-model tool choice, cognitive quality, provider availability, arbitrary shell commands, or the behavior of a harness revision or Desktop carrier that was never tested. No executed-carrier claim follows from their union.

## 3. Carrier binding and claim ledger (read-only)

The mediation profile targets the installed Windows ZCode Desktop application. The rig's binding to that carrier is **read-only**: record the installed binary/build identity, the effective hook configuration and registration, client launch/CWD/profile resolution paths, and hook executable/host image digests by inspection only — no mutation, no redirect, no dev-mode launch, no executed comparison against the live install. Record whether the installed build can be reproducibly mapped to the analyzed source *and* relevant effective configuration; a binary or version match is a provenance finding, not an executed-behavior equivalence proof. A divergence or unmapped packaging/runtime branch is a typed finding for owner adjudication, not something the rig repairs by executing the installed application.

The previously considered executed-binding options — redirecting the installed Desktop to a mock provider, or running a source/dev-mode Desktop build for comparison — are **removed**: both are the contamination class demonstrated by the 2026-09-25 PoC (official-install state mutation visible in the production UI; browser reinstall). The harness's filesystem/database/network side-effect surface on the owner machine is unmapped, so the previous isolation claim for real-harness execution here was not substantiated; that is why executed-carrier proof is out of scope for this rig, not merely deprioritized.

If a future change to the harness or profile makes executed-carrier proof materially necessary, the owner may commission it in a genuinely disposable environment (for example a dedicated VM) as an explicit separate decision with its own isolation contract; the rig never silently upgrades to it.

## 4. Reproducibility and operational contract

A run records the Runtime/host/hook SHA and executable digests, Foundation/Devkit pins, the analyzed harness source revision and analysis-artifact revision, the replay-corpus revision with payload provenance, the read-only installed-carrier identity snapshot, configuration/profile hashes, scenario catalogue revision, Windows/toolchain identity and environment isolation, plus separate outcome artifacts for both layers. A harness revision change, installed-Desktop update, changed hook registration/payload, or Runtime acceptance-code change invalidates the relevant binding until requalified. The rig stays local and deterministic throughout — no model API, no public network, and **no real-harness build or execution on the owner machine**. Make runs bounded by independent process custody and timeouts, with a clean temporary root and failure artifacts retained.

The corrective wave from [ADR-0054](00-adr-0054-typed-identity-law.md) resolves the **transaction-level** hello/event deadline contract and adds preflight SessionStart coverage. The preflight must assert registration and the expected allow/deny semantics, not merely "a host verdict returned". The kit builder packages the effective profile/config and runs its entrypoint from the same CWD and directory layout used by the installed kit. For any hook configuration that can block the owner's ordinary work, keep an immediately executable rollback path.

## 5. Exit rule and relation to later work

The exact candidate receives separate verdicts: **mediation** (Layer 1 at the exact head, invariant map and captured-payload replay), **harness-source contract** (pinned analysis and delegation disposition), and **installed Desktop carrier** (provenance/configuration inspected read-only, with executed behavior explicitly **NOT_PROVEN**). A future surrogate run is a fourth, independently named verdict; its success cannot change the Desktop verdict. The earlier rule that a surrogate CLI plus analysis can close MVP-4 for the existing Desktop profile is withdrawn: under the current real-H1 wording of ADR-0047/0050, this rig does **not** establish the required installed-carrier behavior and must report H1 **OPEN**. The owner may later decide on a narrower acceptance target and formally amend ADR-0047/0050, obligations, Runtime exit matrix and current state, or commission carrier evidence in a genuinely disposable environment under a separate authorized plan. Until such a canonical transaction, do not report MVP-4/H1 complete or advance dependent MVP-5/CA sequencing from these partial verdicts. The no-real-harness-on-owner-machine boundary remains in force for this proposed rig. Other MVP slices do not inherit this proof vehicle automatically.
## 6. Residual risks and falsifiers

A green replay-plus-analysis result can still become fidelity theater: a stale harness pin, a source path that behaves differently under runtime configuration, an analysis that misses a write-capable tool entry, or a carrier-identity drift. Falsifiers are: an unaccounted tool entry (the recorded live instance: subagent child runtimes carry no hook runner, so their tool calls are an unmediated write path — `MEM-20260926T195500Z-F1E2D3`), an installed-build identity diverging from the analyzed revision, a runtime-configuration branch that contradicts the recorded source contract, a historical implementation passing its supposedly discriminating regression, a deny with a side effect in Layer 1, or an outside-scope allow without a registered session. A design-level falsifier: any rig step that builds, executes, or mutates a real harness component on the owner machine — that is a contract violation, not an accepted technique. Any falsifier blocks the affected claim and goes back to design and the owner; it is not handled by repeating an owner-live trial.
