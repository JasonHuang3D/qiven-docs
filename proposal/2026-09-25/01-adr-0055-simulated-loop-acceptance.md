# ADR-0055 (draft): Deterministic Mediation Acceptance with an Explicit Desktop Claim Boundary

> Status: PROPOSED for owner adjudication and canonical landing in `qiven-context`. Companion: [ADR-0054](00-adr-0054-typed-identity-law.md) and [evidence audit](02-h1-trial-history-and-defect-evidence.md).

## 1. Decision and exact supersession

Retire the **four-failure owner-operated GUI probe sequence** as the routine MVP-4 acceptance producer. Replace its mechanical enforcement tests with a scripted, reproducible real-hook/real-host/real-harness rig. This is a proposed amendment to the **real H1 rerun** in [ADR-0050 decision 8](https://github.com/JasonHuang3D/qiven-context/blob/main/decisions/ADR-0050.md), its active obligation/roadmap, and the **real H1 tool-entry proof** in [ADR-0047 decision 6](https://github.com/JasonHuang3D/qiven-context/blob/main/decisions/ADR-0047.md). These older clauses remain authoritative until the owner accepts and the canonical contracts/state are amended; the PR itself changes no gate. [ADR-0036's handoff boundary](https://github.com/JasonHuang3D/qiven-context/blob/main/collaboration/human-handoff-boundary.md) remains applicable to owner-only credentials, external isolation, owner-named trust anchors and adjudication; this proposal does not waive those classes. [ADR-0049's H1 kit standard](https://github.com/JasonHuang3D/qiven-context/blob/main/decisions/ADR-0049.md) remains in force for future actual H1 packages.

The user-facing target is a **Windows ZCode Desktop session** under `zcode-jason-context-record-mvp`. A source-built CLI may share the harness core but is not evidence that the installed Desktop application's packaging, registration, effective configuration and launch environment are identical. The acceptance report must label the precise carrier it proves.

## 2. Two executable layers

**Layer 1 — real hook/host, scripted payloads.** On Windows, invoke the production hook executable and production RuntimeHost through the real pipe, with a fresh isolated installation and captured/pinned harness payload schemas. Exercise the *entire session lifecycle*: boot, SessionStart registration, capability check, PreToolUse for Bash/Write/Edit, PostToolUse correlation, shutdown, and new-session/restart cases. Run both positive and negative controls. Assert response **class** and journal state, not merely that a pipe round trip returned something: SessionStart must create exactly the expected session; a governed mutation must deny without a transaction that executes an effect; an outside-scope action in a *registered, healthy* session must be `not_governed`; missing host/admission/replay/version/secret skew must fail in their specified classes. Include the trial-4 hello/event deadline regression, trial-3 multi-frame and admission regressions, trial-2 payload-lifetime regression, trial-1 absent-payload-field regression, and the separate kit-entrypoint failure. Use real filesystem fixtures for aliases, relative bases, Unicode and reparse/ambiguous cases where the declared scope requires them.

The scenario catalogue is a versioned matrix keyed by **boundary and invariant**, with an explicit coverage map and a failing historical implementation/negative control per incident. Run at least 100 named deterministic experiments as the owner's mandatory breadth floor, and require the boundary/invariant coverage map to pass; the number alone is not sufficient and a Cartesian product of impossible states has no value. Preserve the owner's six original probes as a named subset, but do not treat six probes as the complete matrix. Layer 1 is a Windows gate task; the accepting candidate must have a successful run at its exact head.

**Layer 2 — real harness enforcement with a local mock provider.** Build the actual ZCode agent CLI from a recorded harness source revision and build digest. Configure its *real provider transport* to a local scripted mock model endpoint; do not replace the harness tool executor, hook router, decision parser or result-to-model turn. Start a clean session with the real hook configuration and real host. The mock emits tool-call turns for Bash/Write/Edit and receives the harness's returned observations; scripts include multi-turn continuation after denials and successful outside-scope actions. Assert that SessionStart really fired, the correct PreToolUse ran before each tool, host verdict and hook exit/deny contract reached the harness, **a denied tool produced zero target side effects**, an allowed outside-scope tool executes, PostToolUse and the subsequent model-visible result follow the actual harness behavior, and expected faults fail closed. Sentinels in disposable paths and journal/host/harness logs make the effect assertions independent of output phrasing. If the real harness permits alternate streaming/tool-call encodings or retries on this path, pin and exercise those shapes; do not manufacture a fake path that bypasses the parser. Layer 2 is a reproducible acceptance gate on the **exact Runtime candidate plus harness pin**, and reruns when hook/IPC/harness behavior changes.

A local mock proves how the real harness routes and enforces scripted tool calls. It does not prove real-model choice of tools, cognitive quality, provider availability, or the semantics of arbitrary shell commands.

## 3. Desktop binding and claim ledger

Before claiming **MVP-4 accepted for the intended Desktop profile**, bind the Layer-2 harness revision to the actual installed Desktop application. Record the installed binary/build identity, effective hook configuration and registration, client launch/CWD/profile resolution, hook executable and host image digests, captured payloads, and the evidence that the same parser, hook-decision and tool-execution contract applies. Prefer an automated Desktop/dev-mode run against the local mock when the installed build supports it; use an automated installed-artifact configuration/launch smoke plus direct behavior comparison when a release build cannot redirect its provider. A *source-built dev-mode Desktop* alone is not an installed-build equivalence proof. Any discrepancy triggers a narrow Desktop integration test or an explicit claim downgrade.

If that binding cannot be demonstrated without owner hands, Layer 1 and CLI Layer 2 may pass as **CLI/hook/host mediation evidence**, but the Desktop-profile MVP-4 exit remains **NOT ACCEPTED**. Do not convert an optional owner smoke into a hidden mandatory trial or claim that CLI evidence alone covers the application the owner actually uses. The owner may accept a deliberately narrower CLI-only milestone in a separate canonical scope decision; it must be named as such. No human GUI trial is required by default merely to check mechanical scenarios.

## 4. Reproducibility and operational contract

A run records the Runtime/host/hook SHA and executable digests, Foundation/Devkit pins, ZCode harness source commit and build digest, installed Desktop build when the Desktop claim is made, configuration/profile hashes, mock protocol fixture revision, scenario catalogue revision, Windows/toolchain identity and environment isolation, plus separate outcome artifacts for both layers. A pin change, installed-Desktop update, changed hook registration/payload, provider-tool parser change, or Runtime acceptance-code change invalidates the relevant equivalence claim until requalified. Keep a local, deterministic provider; no model API or public network must be required to pass the mechanical gate. Make runs bounded by independent process custody and timeouts, with a clean temporary root and failure artifacts retained.

The corrective wave from [ADR-0054](00-adr-0054-typed-identity-law.md) resolves the **transaction-level** hello/event deadline contract and adds preflight SessionStart coverage. The preflight must assert registration and the expected allow/deny semantics, not merely "a host verdict returned". The kit builder packages the effective profile/config and runs its entrypoint from the same CWD and directory layout used by the installed kit. For any hook configuration that can block the owner's ordinary work, keep an immediately executable rollback path.

## 5. Exit rule and relation to later work

The exact candidate receives two separately reported verdicts: (a) mechanical hook/host/CLI mediation, requiring both layers green with the invariant coverage map; (b) Desktop-profile binding, requiring installed-carrier evidence above. **MVP-4 for the existing profile exits only with both verdicts green** and any remaining owner-reserved H2/authority step completed. Do not move MVP-5/CA sequencing by treating partial CLI evidence as the Desktop exit. On acceptance of this ADR, amend ADR-0050's specific H1/MVP-4 clause, ADR-0047's proof wording, relevant Runtime exit matrix, obligation and current-state files **in the authorized canonical transaction**. The current proof vehicle for CA-2 and future MVP slices is not automatically changed.

## 6. Residual risks and falsifiers

A green mock-provider run can become fidelity theater if the harness pin is stale, a provider adapter is stubbed, or the installed Desktop uses a different path. A hundred scenarios can miss a single write-capable tool or path escape. Falsifiers are an unaccounted Desktop tool entry, a pinned-versus-installed behavior difference, a historical implementation passing its supposedly discriminating regression, a deny with a side effect, or an outside-scope allow without a registered session. Any falsifier blocks the affected claim and goes back to design and the owner; it is not handled by repeating an owner-live trial.
