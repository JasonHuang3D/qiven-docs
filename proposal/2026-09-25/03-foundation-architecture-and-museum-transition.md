## 1. Finding and authority

The [original Foundation architecture at bootstrap](https://github.com/JasonHuang3D/qiven-foundation/blob/cfecc8b9bfe2ef6fffb3cc30befdec6cb17318c6/docs/architecture/foundation.md) and the [live document](https://github.com/JasonHuang3D/qiven-foundation/blob/9045feee0c81fa247dec49407e51e891fe427744/docs/architecture/foundation.md) declare “low-level, reusable C++ building blocks,” admission only when “broadly useful,” no wrapper around **every** OS/standard-library facility, no hidden expensive work, and convenience alone insufficient. The text does **not** literally prohibit every higher-level abstraction. Reading these clauses as a ceiling that rules out owning compositions or requires multiple consumers is nevertheless an unsafe interpretation: it leaves each higher layer to guess the same lower-level semantics. The repository's unchanged §15 admission questions still have no explicit first-real-consumer completeness requirement. Git history establishes the wording; attribution of its authorship to a particular model comes from the owner, not Git metadata.

[ADR-0007](https://github.com/JasonHuang3D/qiven-context/blob/c73b2288bb1dabfa87a5c222eeab0d7bae6ac2ff/decisions/ADR-0007.md) explicitly said to keep conveniences above Foundation until repeated demand and required multiple downstream consumers to revisit placement. Its header already says **superseded**. [ADR-0024](https://github.com/JasonHuang3D/qiven-context/blob/c73b2288bb1dabfa87a5c222eeab0d7bae6ac2ff/decisions/ADR-0024.md) superseded that threshold on 2026-09-15: one serious consumer is sufficient when the semantic owner is clear, and the first serious implementation should land at that owner. [ADR-0008](https://github.com/JasonHuang3D/qiven-context/blob/c73b2288bb1dabfa87a5c222eeab0d7bae6ac2ff/decisions/ADR-0008.md) (ownership/failure/allocation), [ADR-0009](https://github.com/JasonHuang3D/qiven-context/blob/c73b2288bb1dabfa87a5c222eeab0d7bae6ac2ff/decisions/ADR-0009.md) (distinct ABI/IPC/wire/persistent boundaries), [ADR-0017](https://github.com/JasonHuang3D/qiven-context/blob/c73b2288bb1dabfa87a5c222eeab0d7bae6ac2ff/decisions/ADR-0017.md) (semantic layering), and ADR-0024 remain live constraints. The architecture correction is to apply these together, not to discard portability or explicit cost.

The current surface is real: [public headers](https://github.com/JasonHuang3D/qiven-foundation/tree/9045feee0c81fa247dec49407e51e891fe427744/include/qiven), [unit/header tests](https://github.com/JasonHuang3D/qiven-foundation/tree/9045feee0c81fa247dec49407e51e891fe427744/tests), and [CI](https://github.com/JasonHuang3D/qiven-foundation/blob/9045feee0c81fa247dec49407e51e891fe427744/.github/workflows/ci.yml) cover primitives, Debug/Release, Windows/Linux/macOS and a Linux sanitizer/no-exceptions configuration. The visible CI workflow is `workflow_dispatch`; a successful build or sanitizer run cannot by itself establish that a Runtime consumer uses the correct lower semantic contract. The missing gate is **consumer-linked semantic proof and an active-document consistency check**, not the absence of every mechanical test.

## 2. Proposed replacement Foundation contract

This paragraph set is a candidate **documentation reconciliation** for a new active `docs/architecture/foundation.md` and the corresponding Context authority pointers. Preserve the old words in history. Review the candidate against actual public APIs, platform support and accepted ADR-0024 before canonical adoption. Its purpose is to make existing semantic ownership, explicit costs and first-real-consumer rules discoverable from active entry points; it does not authorize a new whole-infrastructure program, require wholesale third-party adoption, or condition the MVP-4 simulated H1 test on new Foundation code.

1. **Admission by semantic owner and first real consumer.** Before a dependent implementation, list its invariants, owner, lifetime, failure channel, bounds, concurrency, platform cases, and observable resource cost. Place a stable, product-independent semantic operation in Foundation if Foundation owns it, even if there is one consumer and even if it composes multiple primitives, owns memory, or wraps an OS operation. Do not demand repeated consumers or minimal primitive count as a proxy for correct ownership. Product policy, cognition-specific admission, transaction policy and process supervision remain above Foundation; an unknown contract calls for a bounded disposable probe with explicit falsifier.
2. **Complete the admitted operation.** A lower API that exposes only `ByteCursor`/`ByteWriter` primitives is complete for borrowed bounded cursors, not for an owning bounded growing builder. Likewise a lexical path parser is not proof of filesystem authorization. For each admitted consumer, either implement the owned/bounded composition at its lower semantic owner with explicit cost/failure/limit, or record why the needed semantics belong to a named higher layer. A general ban on “high-level encapsulation” is rejected; no abstract maximum abstraction height governs admission. Hidden expensive work is still prohibited: make allocation, filesystem I/O, locking and failure observable in the API.
3. **Public-contract and consumer proof.** Publish an operation contract and exact source baseline before the first dependent Runtime change. Require lower unit tests for malicious/boundary input and representation/lifetime cases; require consumer integration tests that compile/link the exact lower revision and exercise the real call path, including a negative test against the previous defect; test Windows-native alias/reparse/path cases on Windows when relevant. Record the receipt for the **same candidate SHAs** and show which hand-coded upper path was removed. A Foundation-only green test does not close an upper-layer boundary.
4. **Invariant-preserving boundaries.** Keep downward dependencies, explicit lifetime/allocator provenance, checked arithmetic, platform isolation and no-exception consumers; separate C++ object layout from module ABI, IPC, wire, persistence and shared memory. A public C++ type cannot silently authorize a path, define a wire frame, or make a Python operator obey it. If a security or transaction policy spans two frames or layers, the policy's owning layer publishes the whole operation and Foundation supplies only semantically lower pieces.
5. **Discovery and enforcement.** The active README, AGENTS entry, capability inventory and test contracts point to one current architecture and accepted Context decisions. The [Devkit precedent/gate audit](04-devkit-standards-and-precedent-gate.md) proposes the corresponding cross-repository evidence and independent-oracle check. A machine-readable capability row distinguishes `landed`, `admitted-not-yet-landed` and `historical`, names the header/contract/consumer and pinned proof; it must not treat a design proposal as a delivered header. Add a check that active entry points do not cite museum documents as governing law, flag known contradictory phrases/topology, and fail for a missing contract/proof on an admitted new capability. Search cannot prove absence of every latent bug; record its scope.

These are criteria for **specific future work admitted at its actual semantic owner**. They do not command speculative Foundation completion. The [H1 incident audit](02-h1-trial-history-and-defect-evidence.md) distinguishes an external payload assumption, a dangling borrowed span, a host one-frame/client-admission mismatch and a deadline split. The [simulated gate](01-adr-0055-simulated-loop-acceptance.md) turns these into independently falsifiable scenarios; it does not choose a new path library or assign all four defects to Foundation.

## 4. One reviewable implementation transaction after owner decision

1. **Accept the authority delta.** In Context, publish a successor/amendment that explicitly governs Foundation admission, rejects the “only primitive/no higher composition” inference and reconciles ADR-0039/0043 and ADR-0018/0052. Ratify the exact museum list; retain history and update indexes/status as one Context candidate. Do not cite this qiven-docs draft as a substitute for acceptance.
2. **Replace entry points together.** In a separate Foundation candidate, preserve snapshots under `docs/legacy/`, replace `foundation.md`, retire the stale global architecture and completed plans, update `README.md`, `AGENTS.md`, `capability-surface.yaml`, design links and `result.hpp`'s comment. Use current tool paths, actual public headers and actual workflow triggers. Do not mark unbuilt APIs as delivered.
3. **Prove the doc transition.** At the exact candidate head, run a docs/link/index check and a non-museum reference scan for obsolete normative ADR-0007 placement, sealed Host/DCR topology, stale “implementation follows,” dead script commands and dead paths. Keep allowed historical quotations only with clear historical labels. Validate the live Context project entry/decision index and the Foundation capability inventory's resolvable pointers.
4. **Keep engineering implementation separately admitted.** This documentation transaction does not land ByteBuilder, `qiven::fs`, path normalization or an IPC rewrite, and does not gate the interim MVP-4 simulation on any of them. A real detected defect can separately require lower-owner remediation with a tested consumer; state that scope in its own design and exact-head receipt.
5. **Record document receipts and limits.** Attach the affected Context/Foundation document SHAs, pointer-resolution results, allowed historical links and unresolved owner decisions. A clean museum/reference gate proves entry-point accuracy, not Runtime correctness, model continuity or installed Desktop behavior.

Historical document archival reduces cold-start noise; the cross-boundary gate is what prevents a fresh wrong implementation. Both are required for this proposal's acceptance.
